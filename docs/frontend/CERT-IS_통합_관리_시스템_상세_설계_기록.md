## 1. 문서 목적과 자료 범위

이 문서는 CERT-IS 통합 관리 시스템에 관한 현재 요청과 이전 설계 대화, 원본 계획서와 내장 WBS, 수업 평가 가이드라인, 회의 캡처와 UI 스케치를 구조화한다. 단순한 기능 요약이 아니라, 기능이 어디에 속하는지, 사용자가 어떤 화면을 오가는지, 어떤 규칙을 확정했는지, 어떤 초기 제안이 수정됐는지, 구현 전에 무엇을 더 결정해야 하는지를 남긴다.

사용자가 직접 정한 요구사항과 이전 답변에서 제안한 구현 방향은 구분한다. 아직 정하지 않은 정책은 편의상 확정하지 않는다.

### 1.2 상태 표기 원칙

| 표기 | 의미 |
|---|---|
| **확정** | 사용자가 직접 명시하거나 후속 발언으로 정한 요구사항 |
| **방향 합의** | 사용자가 긍정적으로 수용했거나 선호를 밝혔지만 구체 정책·상세 UI는 남아 있는 방향 |
| **제안** | 이전 답변에서 설명한 설계·구현 예시. 사용자가 구현 선택까지 확정한 것은 아님 |
| **계획서 명시** | 원본 계획서·WBS에 적힌 계획. 실제 완료나 최신 요구와의 일치까지 의미하지 않음 |
| **회의 검토안** | 팀 대화에서 검토한 안. 후속 설명과 대조해 적용 여부를 판단해야 함 |
| **미정** | 논의되지 않았거나 선택지가 남아 있는 사항 |
| **이전안** | 과거 검토했으나 후속 요구사항으로 대체된 안 |
| **자료 확인 필요** | 추가 원본 또는 더 명확한 판독·후속 설명이 필요한 내용 |

우선순위는 **최신 사용자 설명 → 이전 사용자 설명 → 답변의 제안**이다. 계획서의 개발 범위와 다르면 한쪽을 지우지 않고 차이를 기록한다. 계획서에만 있는 기술·배경·AI 기본 명세는 원본대로 추가하고, 팀 합의가 필요한 범위 변경은 따로 남긴다. 답변의 “거의 확정”이라는 표현만으로 기능 전체나 기술 선택까지 확정됐다고 보지 않는다.

## 2. 시스템 개념과 기획 방향

### 2.1 시스템이 다루는 범위

CERT-IS 통합 관리 시스템은 동아리의 프로젝트·스터디 활동, 활동 안에서의 대화와 회의 기록, 개인 및 팀 일정, 동아리방 예약을 한 애플리케이션에서 다루는 구상이다. 계획서의 명칭은 `CERT-IS 통합 관리 시스템`이고 WBS 제목은 `CERT-IS Hub 프로젝트 WBS`다. 이전 답변에도 `CERT-IS Hub`라는 표현이 사용됐다. 실제 UI의 표시 명칭을 통일할지는 별도 정한다.

사용자 한 명은 여러 프로젝트나 스터디에 동시에 참여할 수 있다. 따라서 특정 프로젝트 화면과 사용자의 활동 전체를 보는 전역 화면을 구분해야 한다.

| 범위 | 중심 대상 | 포함 기능 |
|---|---|---|
| 전역(Global) | 로그인한 개인과 동아리 전체 | Dashboard, 개인 통합 캘린더, 동아리방 예약 진입, 개인 AI 추천, 설정 |
| 활동 공간(Workspace) | 선택한 프로젝트 또는 스터디 | 팀 캘린더, 다중 채팅방, 태그 및 태그 그룹, 채팅방에 연결된 Markdown 회의록, 예약 진입 |

전역과 Workspace는 기능의 소속과 탐색 범위를 구분하는 개념이다. 두 개의 독립 시스템을 만든다는 뜻은 아니다.

### 2.2 프로젝트와 스터디

- **확정:** 프로젝트와 스터디의 UI는 기본적으로 동일하다.
- **확정:** 현재까지는 어느 한쪽에만 필요한 특별한 추가 기능이 확인되지 않았다.
- **제안:** 공통 개념을 `Workspace`로 표현한다.
- **제안:** 데이터에 `type: project | study`를 두고 공통 화면과 경로를 사용한다.
- **미정:** 스터디 생성·수정 권한이 프로젝트의 팀장 권한과 정확히 같은지, 구분에 따른 운영 규칙이 필요한지는 별도 결정한다.

“현재 추가 기능이 없다”는 발언을 앞으로도 차이가 절대 생기지 않는다는 정책으로 확대하지 않는다.

### 2.3 전체 정보 구조

```text
CERT-IS 통합 관리 시스템
├─ Global
│  ├─ Dashboard: 로그인 직후 홈
│  ├─ 개인 통합 캘린더
│  ├─ 동아리방 예약 진입
│  ├─ AI 보안 분야 추천: 전역·개인, Gemini 진단 분석과 학습 방향 제시
│  └─ 설정: 세부 항목 미정
│
├─ Project / Study Workspace
│  ├─ 프로젝트 홈: 기본적으로 팀 캘린더
│  ├─ 프로젝트 일정
│  │  ├─ 팀 전체 일정 확인
│  │  └─ 담당자·담당업무 확인 및 개인 일정 우선 표시
│  ├─ Chat
│  │  ├─ 여러 채팅방 생성
│  │  ├─ 채팅방별 참여자 구성
│  │  ├─ 태그를 통한 검색·정렬
│  │  ├─ 프로젝트별 Tag Group과 태그 순서
│  │  └─ 채팅방에 연결된 회의록.md
│  └─ 메인 작업 화면 전환
│     ├─ 팀 캘린더
│     ├─ Markdown 문서·회의록 편집/조회
│     └─ 일정 신청·동아리방 예약 화면
│
└─ 공통 동아리방 예약 기능
   ├─ Global 진입: 프로젝트 + 시간대 선택
   └─ Workspace 진입: 현재 프로젝트 지정 + 시간대 선택
```

위 구조는 확인 가능한 논의의 기능 관계를 표현한다. 상세 메뉴 순서, 화면 배치, URL, 구현 이름까지 모두 확정됐다는 의미는 아니다.

## 4. 전역 화면과 Dashboard

### 4.1 로그인 직후 화면

**확정:** 로그인 직후 홈은 Dashboard이다. 사용자는 이전에 제안한 Dashboard 구성이 괜찮을 것 같다고 밝혔다.

Dashboard에 제안된 항목은 다음과 같다.

| 항목 | 역할 | 결정 수준 |
|---|---|---|
| 내 프로젝트 | 참여 중인 프로젝트·스터디로 이동 | 내용 후보 |
| 다가오는 일정 | 가까운 개인·활동 일정을 확인 | 내용 후보 |
| 최근 채팅 | 최근 대화가 있는 활동/방으로 이동 | 내용 후보 |
| 동아리방 예약 현황 | 현재 또는 예정된 예약을 확인 | 내용 후보 |

홈의 존재는 확정됐지만 카드 개수, 순서, 정보량, 기간 기준, 알림 기능, 참여하지 않은 프로젝트 노출 여부는 확정되지 않았다.

### 4.2 전역 기능의 진입 위치

캘린더, 예약, AI 추천은 전역 기능으로 둔다. 다만 사용자가 말한 좌측 1열의 목록은 `접기/펼치기·홈·목록·생성·설정`이었다. 따라서 전역 기능을 모두 좌측 1열의 개별 버튼으로 추가하는 것은 아직 확정안이 아니다. 홈의 버튼, 상단바, 별도 메뉴 등 실제 진입 위치는 와이어프레임에서 정한다.

### 4.3 AI 추천

- **확정:** 전역에 속한 개인 기능이다.
- **계획서 명시:** 진단 문항에 응답하면 Gemini API가 분석하여 적합한 보안 분야와 학습 방향을 제시한다. 신입부원의 프로젝트·스터디 선택을 지원하려는 목적이다.
- **미정:** 진단 문항, 보안 분야 목록, 프롬프트, 결과 화면, 저장 여부, 실패 처리 등 상세 정책.
- 사용자는 대화 당시 “뭔기능인진 나도 몰라. 내 아이디어 아님”이라고 밝혔다. 이는 당시 사용자가 상세를 모른다는 맥락으로 보존하며 계획서에 기본 명세가 없다는 의미로 확대하지 않는다.
- `/ai`는 제안 경로이며 실제 URL 확정과는 구분한다.

AI 기능을 회의록 자동 요약, 일정 최적화, 프로젝트 추천 등으로 임의 정의하지 않는다. 회의록은 현재 논의상 사람이 Markdown을 작성하는 구조다.

계획서는 자체 AI 모델 학습을 제외하고 Gemini API 호출만 사용한다고 명시한다. AI 담당자의 업무와 10~12주차 일정은 21절 및 23절에 보존한다.

## 5. Workspace 홈과 작업 화면

### 5.1 프로젝트 홈의 의미

**확정:** 프로젝트 홈은 별도의 대단한 대시보드가 아니라, 프로젝트를 선택한 뒤 작업 화면을 전환하는 공간이다.

사용자가 설명한 화면은 다음 사이를 오간다.

1. 팀 캘린더를 띄운다.
2. Markdown 편집기를 띄워 문서·회의록을 편집하거나 조회한다.
3. 일정 신청 창 또는 동아리방 예약 기능을 연다.
4. 채팅방을 선택하면 대화 내용을 본다.

**확정:** 프로젝트 진입 시 기본적으로 팀 캘린더를 띄운다. 전체 애플리케이션의 Dashboard와 프로젝트 홈은 다르다.

### 5.2 전환 시 유지할 탐색 구조

사용자는 좌측 2열을 “어지간하면 채팅 고정”으로 설명했다. 프로젝트 메인 화면에 캘린더나 문서 같은 다른 내용이 들어갈 수 있기 때문이다.

따라서 기본 방향은 다음과 같다.

```text
전체 탐색 1열 | 현재 Workspace의 채팅 탐색 2열 | 메인 작업 콘텐츠
                                              ├─ 팀 캘린더
                                              ├─ 채팅 내용
                                              ├─ Markdown 편집/조회
                                              └─ 예약·신청 화면
```

**미정:** “어지간하면”이라는 표현의 예외, 좁은 화면에서 2열을 숨기는 방식, 문서 화면에서 채팅과 나란히 표시하는 방식은 아직 정하지 않았다.

### 5.3 일정 신청이라는 표현

최신 사용자 발언에는 “일정 신청 창”이 등장하고 이전 답변에서는 이를 동아리방 예약 화면과 연결했다. 현재 자료만으로 별도의 일정 승인 시스템이 있다고 확정할 수 없다. 예약 화면을 가리키는지, 일반 프로젝트 일정 생성도 포함하는지 추가 확인해야 한다.

## 6. 좌측 탐색과 화면 구조

### 6.1 좌측 1열: 전체 애플리케이션 탐색

| 구성 | 확인된 역할 | 남은 결정 |
|---|---|---|
| 접기/펼치기 | 1열 표시 크기·형태 전환 | 접었을 때 아이콘, 상태 저장 방식 |
| 홈 | 전역 Dashboard 이동 | 정확한 버튼 모양·위치 |
| 목록 | 프로젝트·스터디 탐색 | 참여 공간만 표시할지, 전체 목록과 나눌지 |
| 생성 | 프로젝트·스터디 생성 진입 | 생성 권한과 표시 조건, 생성 양식 |
| 설정 | 설정 진입 | 개인/Workspace/운영 설정의 구분 |

**계획서 명시:** 프로젝트·스터디 목록에서는 담당자·상태·보안 분야 기준 필터링을 제공한다. 실제 필터 조작을 1열, 목록 페이지 또는 상단 어디에 둘지는 미정이다. 이는 채팅방 태그 필터와 별개의 활동 목록 필터다.

사용자는 이 부분을 “개발 방법론적으로 접근 필요”라고 표현했다. 화면 목록과 상태를 먼저 정하고 구현 구조로 내려가는 접근이 후속 답변에서 제안됐다.

### 6.2 좌측 2열: 채팅 탐색기

**확정된 방향:** 프로젝트 선택 시 채팅 탐색을 중심으로 사용한다. 일반적인 `개요·채팅·회의록·일정` 메뉴만 나열하는 사이드바가 아니다.

**제안된 구성:**

- 현재 프로젝트·스터디 이름.
- 채팅방 검색.
- 태그 및 Tag Group을 이용한 탐색·정렬.
- 채팅방 목록.

채팅방 생성 버튼과 초대 버튼의 실제 위치는 정하지 않았다.

### 6.3 상단바와 채팅 화면

사용자는 채팅 화면을 “상단바, 채팅방 목록, 채팅 내용”으로 설명했다. 이 세 요소를 보존하되 상단바가 앱 전체 상단인지, Workspace 상단인지, 채팅방 헤더인지 단정하지 않는다. 제공된 스케치에는 상단 띠가 있지만 구체적인 기능 이름이 적혀 있지 않다.

## 7. 채팅방 구조

### 7.1 프로젝트 안의 다중 채팅방

**확정:** 프로젝트 내부에서 여러 채팅방을 생성한다. 프로젝트당 한 방으로 제한하는 것이 최종 아이디어가 아니다.

사용자는 한 개로 줄였던 것은 능력·구현 여건 때문이며 원래 아이디어는 여러 채팅방이었다고 정정했다. 원본 계획서에는 일정에 따라 프로젝트·스터디별 한 방으로 제한한다는 위험 대응이 있고 WBS 8.1에는 `방 1개 고정`이 적혀 있다. 회의 캡처에서도 먼저 활동별 한 방을 구현하고 나중에 나누자는 논의가 확인된다. 따라서 **최신 설계 요구는 다중 채팅**, **계획서·회의의 축소 구현안은 활동별 한 방**으로 남긴다. 다중 방을 이번 학기 실제 구현 범위에 포함할지는 팀과 재조정이 필요하다.

방을 나누는 구체 기준은 강제되지 않았다. 이전 답변의 `일반·공지·개발`은 예시이고, 사용자가 직접 제시한 회의방 예시는 `n주차 회의`다.

### 7.2 채팅방별 참여자

- **확정:** 채팅방마다 서로 다른 사람을 초대할 수 있다.
- **확정:** 동일한 참여자 구성의 채팅방을 여러 개 만들 수 있다.
- **확정:** 채팅방 생성은 누구나 가능하다.
- **미정:** 누구나가 해당 프로젝트의 모든 팀원을 의미하는지, 동아리 전체 사용자를 포함하는지 명시적인 범위가 필요하다.
- **미정:** 초대 권한은 방 생성자, 모든 방 참여자, 모든 팀원 중 누구에게 있는가.
- **미정:** 프로젝트 밖 인원을 초대할 수 있는가.
- **미정:** 초대되지 않은 팀원이 방 목록·대화·회의록을 각각 볼 수 있는가.

“누구나 채팅방 생성 가능”과 “누구나 모든 채팅방 열람 가능”은 서로 다른 정책이다. 후자는 아직 정해지지 않았다.

**회의 검토안:** `동아리(관리자) → 팀 A → 채팅방`의 계층을 두고, 팀 B는 팀 A의 방을 보지 못하지만 임원/관리자는 하위 팀 채팅을 볼 수 있게 하자는 아이디어가 있다. 동아리를 거치지 않고 자체 생성한 팀 X의 방에는 임원이 접근하지 못하는 경우도 질문됐다. 이는 최종 권한 명세가 아니라 팀 대화에서 제시한 접근 모델이며 백엔드와 합의가 필요하다고 언급됐다. 24절에 논의 맥락을 보존한다.

### 7.3 기본 이용 흐름

```text
프로젝트 선택
→ 채팅방 생성 또는 기존 채팅방 탐색
→ 참여자 구성
→ 태그를 붙여 분류
→ 대화 기록 누적
→ 필요할 때 연결된 Markdown 회의록 편집/조회
```

이 흐름은 기능의 연결을 표현하며, 실제로 태그 선택이나 초대를 생성 시 필수 입력으로 강제한다는 뜻은 아니다.

### 7.4 실시간 통신과 초기 구현 계획

**계획서 명시:** 실시간 메시지 송수신을 제공한다. 기술 구성은 Python·FastAPI·WebSocket이며 WBS에는 채팅 API·WebSocket 연결 관리와 프론트엔드 재연결 처리가 별도 작업으로 있다. 재연결 비고는 `지수 백오프 재연결`이다. 이미 구현된 동작으로 보지는 않는다.

회의에서 데이터베이스를 연결한 한 방이 동작하면 확장 가능하지 않겠느냐는 언급은 있으나 다중 방·팀별 접근·임원 열람을 검증한 기술 결론은 아니다.

## 8. 태그와 태그 그룹

### 8.1 태그의 대상과 기능

**확정:** 태그는 채팅방에 붙인다. 태그를 이용해서 채팅방을 검색하고 정렬할 수 있어야 한다. 개별 메시지에 태그를 붙이는 요구사항은 확인되지 않았다.

### 8.2 태그 그룹의 개념

사용자는 태그 목록을 두고 그룹으로 묶는 개념을 제안했으며 이름을 가칭 “태그 그룹”이라고 했다.

```text
태그 그룹: 주차
├─ 1주차
├─ 2주차
└─ 3주차
```

사용자는 그룹 안의 태그 순서를 바꾼 후 `주차`를 눌러 정렬하면, 그 순서대로 채팅방이 나오는 방식을 설명했다. 단순 문자열 가나다순 정렬만 제공한다는 의미가 아니다.

예를 들어 다음과 같은 관계를 생각할 수 있다.

```text
1주차 회의 채팅방 → 1주차 태그
2주차 회의 채팅방 → 2주차 태그
3주차 회의 채팅방 → 3주차 태그

‘주차’ 그룹으로 정렬
→ 그룹에서 정해 둔 1주차 → 2주차 → 3주차 순서 적용
```

위 채팅방 이름과 관계는 사용자 예시를 구체화한 설명이며 고정된 방 생성 규칙은 아니다.

### 8.3 그룹의 범위

이전 답변에서 태그 그룹을 프로젝트별로 만드는지 시스템 공통으로 만드는지 질문했고, 후속 사용자가 “프로젝트 별로 만들 수 있음”이라고 답했다. 앞선 질문 순서와 답변의 재정리를 근거로 **프로젝트별 태그 그룹 생성 가능**으로 기록한다. 해당 짧은 발언에서 대상을 다시 명시하지 않았다는 점도 보존한다.

### 8.4 추가 결정사항

| 항목 | 현재 상태 |
|---|---|
| 태그 그룹 이름 | 가칭. UI 용어 확정 필요 |
| 그룹 생성·수정·삭제 권한 | 미정 |
| 태그 생성·수정·삭제 권한 | 미정 |
| 방 하나에 붙일 수 있는 태그 수 | 미정 |
| 같은 그룹 안의 여러 태그를 한 방에 붙일 수 있는지 | 미정 |
| 태그 없는 방의 정렬 위치 | 미정 |
| 같은 태그를 가진 여러 방의 2차 정렬 기준 | 미정 |
| 여러 그룹을 동시에 선택할 때 검색·정렬 규칙 | 미정 |
| 순서 변경 UI | 기능 방향은 확인, 드래그 등 조작 방식은 미정 |
| 태그 삭제 시 기존 방의 처리 | 미정 |

## 9. 회의록과 Markdown 문서

### 9.1 채팅이 원본, 회의록은 정리 문서

**확정:** 회의는 `n주차 회의` 같은 채팅방을 만들고 그 방에서 진행하는 구조를 중심으로 한다. 대화 흐름 자체가 남아 내용 유실을 줄인다는 것이 사용자의 의도다.

**확정된 구조:** 해당 채팅방에 연계되는 `회의록.md`가 각각 존재하며, 요약과 정리를 위해 사용한다.

```text
회의 채팅방
├─ 실제 대화: 원본 기록의 중심
└─ 연결된 회의록.md: 사람이 요약·정리하는 문서
```

이전 답변의 `minutes.md`는 같은 관계를 설명하기 위한 예시 파일명이다. 실제 저장 파일명을 영문으로 고정했다는 의미는 아니다.

### 9.2 제공 기능

- **확정:** Markdown 편집.
- **확정:** Markdown 조회.
- **확정된 방향:** 사용자가 직접 작성한다.
- 별도의 큰 회의록 관리 시스템을 만들기보다 채팅방과 연결된 파일로 다루려는 의도다.

**회의와의 관계:** 회의 캡처에는 회의록을 나중에 추가하자는 의견과, 임원진 입장에서는 최소한 생성 가능한 기능이 필요하다는 의견이 함께 있다. 계획서에는 Markdown 등록·조회가 있고 후속 사용자 설명은 연결 문서의 편집·조회로 구체화됐다. “회의록을 버리자”라는 회의 중 표현을 최종 기능 삭제로 취급하지 않는다.

### 9.3 연결 관계와 구현 미정 사항

“채팅방마다 각각 연계되는 회의록”이라는 요구는 확인됐지만, 다음은 아직 정해지지 않았다.

- 방을 만들 때 문서를 자동으로 생성하는가, 사용자가 필요할 때 생성하는가.
- 채팅방 하나에 회의록 하나를 강제하는가, 여러 문서를 허용하는가.
- 모든 방에 회의록을 두는가, 회의용 방에만 두는가.
- 편집·열람 권한은 채팅방 참여자와 동일한가.
- 방 삭제·문서 삭제·프로젝트 탈퇴 시 연결 기록을 어떻게 보존하는가.
- 저장 버튼, 자동 저장, 수정 이력, 동시 편집을 제공하는가.
- 문서를 실제 `.md` 파일로 저장하는가, 데이터베이스에 Markdown 본문을 저장하는가.
- 연결 문서 외에 일반 프로젝트 Markdown 문서를 만들 수 있는가.

사용자는 `md 편집기`를 프로젝트 홈의 화면 전환 대상으로 언급했고 후속 답변에는 `Markdown 문서/회의록`이라는 표현이 있다. 그러나 이를 근거로 일반 문서 관리 전체가 확정됐다고 보지는 않는다.

## 10. 캘린더와 일정 구조

### 10.1 전역 개인 통합 캘린더

**확정:** 전역 캘린더는 개인의 일정을 다룬다. 한 사람이 여러 프로젝트·스터디에 참여할 수 있으므로 활동 하나에 종속된 달력과 구분한다.

**제안된 구성:** 자신이 참여한 여러 프로젝트의 일정, 개인 담당 일정, 동아리 전체 일정을 통합해서 보여준다. 사용자의 개인 중심 요구를 화면 구조로 구체화한 답변의 제안이다.

**미정:** 개인이 프로젝트와 무관한 일정을 별도로 생성할 수 있는지, 통합 캘린더에 팀 전체 일정을 모두 넣을지 담당 일정 위주로 넣을지, 필터의 기본값은 무엇인지.

**계획서 명시:** 동아리 일정·프로젝트 일정·예약을 통합 표시한다. 외부 Google/Notion 캘린더 연동은 구현 제외다.

### 10.2 프로젝트 팀 캘린더

**확정:** 프로젝트 일정은 달력으로 보여준다. 일정에 담당자와 담당업무를 적는다.

**확정된 방향:** 개인 담당 일정을 우선 보여주고, 필요하면 다른 사람의 일정도 확인할 수 있다.

| 정보 | 확인된 의도 | 미정 사항 |
|---|---|---|
| 일정이 무엇인지 | 달력에서 일정 내용을 확인 | 입력 필드와 상세 표시 범위 |
| 담당자 | 누가 맡는지 표시 | 한 명/여러 명 허용 여부 |
| 담당업무 | 담당자가 무엇을 하는지 기록 | 일정 설명과 별도 필드인지 |
| 개인 우선 표시 | 자신의 담당 일정이 먼저 눈에 들어오게 | 필터, 강조, 별도 목록 중 어떤 방식인지 |

### 10.3 일정의 세 범위

이전 답변은 다음 세 레이어로 정리했다.

1. 개인 캘린더.
2. 프로젝트 캘린더.
3. 동아리 전체 일정.

예약 일정은 달력에 표시할 일정 유형 중 하나로 설명됐다. 이를 서로 다른 데이터베이스나 세 개의 독립 캘린더 서비스를 사용하라는 기술 결정으로 해석하지 않는다.

### 10.4 다른 팀원의 일정 열람

**확정:** 프로젝트 내부에서는 다른 팀원의 일정 중 **같은 프로젝트 내용 또는 공개된 것만** 볼 수 있다.

```text
다른 팀원의 일정
├─ 현재 프로젝트에 속함 → 열람 대상
├─ 현재 프로젝트 밖이지만 공개됨 → 열람 대상
└─ 현재 프로젝트 밖이며 비공개임 → 열람 대상 아님
```

이 규칙은 팀원의 모든 활동을 볼 수 있다는 의미가 아니다. 열람 가능한 일정의 세부 필드, 공개의 대상 범위, 공개 설정 권한은 별도 결정이 필요하다.

### 10.5 일정 유형에 따른 표현

| 일정 유형 | 표시 방향 | 상태 |
|---|---|---|
| 내 일정 | 개인에게 필요한 여러 정보를 표시 | 방향 확정, 필드 목록 미정 |
| 같은 프로젝트의 팀원 일정 | 열람 가능하고 담당자·업무를 확인 | 범위 확정, 세부 UI 미정 |
| 공개된 다른 일정 | 공개 범위에 따라 열람 | 원칙 확정, 공개 정책 미정 |
| 다른 팀의 동아리방 예약 | 상세 내용은 숨기고 어느 팀인지 표시 | 확정 |
| 동아리 자체 일정 | 중요한 일정으로 색을 사용해 구분 | 방향 확정, 실제 색상 미정 |

사용자는 일정 종류를 구분해야 한다고 명시했다. 모든 일정에 같은 수준의 상세 정보를 노출하는 UI는 이 요구와 맞지 않는다.

예약 시간대가 이미 사용 중이라는 정보는 예약 탐색에 필요하지만, 다른 팀 예약에서 정확히 어떤 필드까지 보여줄지는 별도 정한다. 팀명 공개와 예약 목적 공개를 같은 것으로 취급하지 않는다.

### 10.6 캘린더의 추가 결정사항

- 월간·주간·일간 중 기본 보기.
- 일정 생성·수정·삭제 권한.
- 일정 공개 범위와 기본값.
- 동아리 전체 일정을 등록·수정하는 역할.
- 담당자 필터의 적용 방식.
- 반복 일정과 일정 알림의 필요 여부. 외부 캘린더 연동은 계획서의 구현 제외 항목이므로 추가 결정 후보와 구분한다.
- 시간대, 날짜 경계, 종료 시각 처리.
- 프로젝트 종료·탈퇴 후 개인 통합 캘린더의 노출 정책.

위 항목은 구현 전에 검토할 사항이며, 이미 요구된 추가 기능 목록으로 보지는 않는다.

## 11. 동아리방 예약

### 11.1 예약 기능의 소속과 두 진입점

사용자는 처음에는 전역 기능으로 할지 프로젝트 내부 기능으로 할지 미정이라고 설명한 뒤, 둘 다 살리고 전역 기능을 프로젝트 안에서 현재 팀 옵션으로 호출하는 방식을 긍정적으로 제시했다. 이후 답변은 이를 공통 예약 기능으로 정리했다.

**방향 합의:** 예약 기능은 하나로 두고, 전역과 Workspace에 진입점을 둔다.

| 진입 위치 | 프로젝트 지정 | 사용자의 주요 선택 |
|---|---|---|
| 전역 | 현재 프로젝트가 정해지지 않음 | 어떤 프로젝트 + 어떤 시간대 |
| 프로젝트 내부 | 현재 프로젝트를 기본 지정 | 어떤 시간대 |

**제안:** 전역에서 작은 모달을 열고 프로젝트와 시간대를 선택한다. 프로젝트 내부에서는 같은 기능에 현재 프로젝트 정보를 넣어 연다.

프로젝트 내부 진입 시 프로젝트 선택이 기본값만 채워지는지, 다른 프로젝트로 변경할 수 없는지까지는 미정이다.

### 11.2 확정된 예약 규칙

| 항목 | 규칙 |
|---|---|
| 예약 신청 | 누구나 가능 |
| 예약 단위 | 30분 |
| 중복 | 선점된 시간과 중복되는 예약은 불가 |
| 운영 관리 | 임원진이 관리 |
| 다른 팀 예약의 공개 | 어느 팀인지 표시하고 상세 내용은 숨김 |

**계획서 명시:** 시간 단위 예약, 중복 자동 차단, 주간 예약 현황판을 제공한다. 이 가운데 일반적으로 적힌 시간 단위는 후속 사용자 설명에서 30분으로 구체화됐다. 주간 현황판은 원본에 있는 요구이며 월간/일간 캘린더 기본 보기와 혼동하지 않는다.

예약 단위는 처음에 10분/30분 두 후보였고, 최신 발언에서 30분으로 확정됐다. 두 후보를 병렬로 남겨 현재 미정처럼 표현하면 안 된다.

### 11.3 중복 규칙의 해석 범위

선점된 예약과 겹치면 중복이라는 의도는 확정됐다. 다만 다음까지 이미 결정됐다고 볼 수는 없다.

- 종료와 다음 시작이 같은 시각이면 연속 예약으로 허용하는가.
- 동아리방 외에 복수 예약 자원이 있는가.
- 승인 대기 예약도 시간을 선점하는가.
- 신청 완료 즉시 확정되는가, 임원 승인 후 확정되는가.
- 여러 30분 슬롯을 한 번에 묶어 예약할 수 있는가.

서로 겹치는 신청을 막는다는 요구와 임원진이 관리한다는 요구만으로 승인제나 특정 예약 상태 모델을 만들어 넣지 않는다.

### 11.4 예약의 추가 결정사항

| 구분 | 추가 결정할 내용 |
|---|---|
| 신청자 범위 | 로그인 사용자, 동아리원, 프로젝트 참여자 중 정확한 범위 |
| 예약 대상 프로젝트 | 자신이 참여한 프로젝트만 고를 수 있는지, 스터디도 대상인지 |
| 개인 예약 | 프로젝트 없이 개인 명의로 예약할 수 있는지 |
| 시간 제약 | 운영 시간, 최소·최대 예약 길이, 예약 가능 기간 |
| 30분 단위 해석 | 시작 시각을 정각/30분으로 제한하는지, 길이만 30분 배수인지 |
| 수정·취소 | 예약자·팀장·임원진의 권한과 마감 조건 |
| 운영 관리 | 승인, 거절, 강제 취소, 시간 변경 등의 실제 관리 범위 |
| 예약 목적 | 입력 여부와 공개 범위 |
| 동시 신청 | 같은 시간을 동시에 신청했을 때 한 건만 확정하는 처리 |
| 일정 연계 | 예약을 팀 캘린더·개인 캘린더에 표시하는 상세 기준 |

### 11.5 공통 UI 컴포넌트 제안

이전 답변에서는 다음 두 표현을 사용했다.

```text
ReservationModal(projectId?)

Global: projectId = null → 프로젝트를 선택
Project: projectId = 현재 프로젝트 → 시간대를 선택
```

```tsx
<ReservationModal workspaceId={currentWorkspaceId} />
```

둘 다 호출 위치에 따라 활동 공간 정보를 넘기는 같은 방향을 설명한다. `projectId`와 `workspaceId` 중 실제 이름은 공통 Workspace 모델 채택 여부와 함께 정한다. React+TypeScript는 계획서에 명시된 기술 구성이다. 다만 이 JSX의 컴포넌트 이름·인자·모달 구현이 최종 API라는 의미는 아니다.

## 12. 역할과 권한

### 12.1 확인된 역할

계획서의 기본 역할 구분은 **임원진 / 일반부원**이며 로그인과 접근 제어를 구현한다. 후속 대화에는 **팀장**이 추가로 등장한다. 팀장은 동아리 전체 역할인지 프로젝트별 역할인지 미정이므로 기존 두 역할을 삭제하거나 무조건 세 개의 배타적인 역할로 바꾸지 않는다.

| 역할·관계 | 확인된 권한·용도 | 제한적으로 해석할 부분 |
|---|---|---|
| 일반 사용자/팀원 | 예약 신청, 채팅방 생성 | ‘누구나’의 정확한 범위 미정 |
| 팀장 | 프로젝트 생성·수정 가능 | 팀장만 가능한지, 임원도 가능한지 미정 |
| 임원진 | 예약 관리 | 구체 관리 동작 미정 |
| 채팅방 참여자 | 방마다 따로 구성되는 대화 인원 | 참여와 열람·초대·문서 편집 권한의 관계 미정 |
| 일정 담당자 | 프로젝트 일정의 담당자·담당업무 표시 대상 | 담당자 지정·수정 권한 미정 |

팀장과 임원진을 서로 배타적인 역할로 확정하지 않는다. 한 사용자가 두 역할을 함께 가질 수 있는지도 아직 정하지 않았다.

### 12.2 권한 결정표

| 동작 | 현재 정책 | 상태 |
|---|---|---|
| 프로젝트 생성·수정 | 팀장이 가능 | 확정 |
| 스터디 생성·수정 | 프로젝트와 같은 UI 사용, 권한 적용은 미확정 | 미정 |
| 예약 신청 | 누구나 가능 | 확정, 범위 추가 정의 필요 |
| 예약 운영 관리 | 임원진 | 확정, 동작 추가 정의 필요 |
| 본인 예약 수정·취소 | 규칙 없음 | 미정 |
| 채팅방 생성 | 누구나 가능 | 확정, 범위 추가 정의 필요 |
| 채팅방 초대 | 방마다 참여자 구성 가능 | 기능 확정, 수행 권한 미정 |
| 채팅방 열람·수정·삭제 | 규칙 없음 | 미정 |
| 태그/태그 그룹 관리 | 프로젝트별 사용 가능 | 기능 확정, 수행 권한 미정 |
| 회의록 편집·조회 | 기능 제공 | 기능 확정, 수행 권한 미정 |
| 프로젝트 일정 생성·수정·삭제 | 규칙 없음 | 미정 |
| 다른 팀원의 일정 열람 | 같은 프로젝트 내용 또는 공개된 일정 | 확정 |
| 다른 팀 예약 상세 열람 | 상세 숨김, 팀만 표시 | 확정 |
| 동아리 전체 일정 관리 | 규칙 없음 | 미정 |

### 12.3 권한별 UI

이전 답변에서는 역할에 따라 생성·수정·예약 관리 버튼을 어디까지 숨길지 질문했다. 후속 사용자 발언으로 프로젝트 생성·수정은 팀장이 가능하고 예약 관리는 임원진이라는 방향이 확인됐다.

**제안:** 권한 표를 먼저 완성하고 각 버튼의 표시·비활성·접근 거절 상태를 정한다. 화면에서 버튼을 숨기는 것과 데이터 접근 권한을 처리하는 것은 별개 구현 과제다. 인증 방식은 계획서에 JWT로 명시돼 있으며 역할 저장 방식과 서버 권한 검증의 상세는 미정이다.

## 13. 라우팅 방향

### 13.1 이전 대화의 URL 제안

**제안:** 공통 활동 공간을 `Workspace`로 표현하고 다음과 같이 URL을 나눈다.

```text
/
├─ /dashboard
├─ /calendar
├─ /reservation
├─ /ai
├─ /settings
│
└─ /workspace/:workspaceId
   ├─ /calendar
   ├─ /reservation
   ├─ /document/:documentId
   └─ /chat/:chatRoomId
```

| 전체 경로 예시 | 의미 |
|---|---|
| `/dashboard` | 전역 홈 |
| `/calendar` | 개인 통합 캘린더 |
| `/reservation` | 전역 예약 진입 |
| `/ai` | 개인 AI 추천 |
| `/settings` | 설정 |
| `/workspace/:workspaceId/calendar` | 선택한 공간의 팀 캘린더 |
| `/workspace/:workspaceId/reservation` | 현재 공간을 지정한 예약 진입 |
| `/workspace/:workspaceId/document/:documentId` | Markdown 문서·회의록 |
| `/workspace/:workspaceId/chat/:chatRoomId` | 채팅방 내용 |

이전 답변의 예시는 `프로젝트 A의 3주차 회의 채팅방`을 `/workspace/12/chat/37`처럼 표현하는 것이다. 숫자 12와 37은 설명용이며 실제 객체 ID가 아니다.

### 13.2 공통 경로를 쓰는 이유

프로젝트와 스터디의 UI가 기본적으로 같으므로 URL을 무조건 `/project`와 `/study`로 나누기보다 공통 경로와 유형 데이터로 구분하자는 제안이다.

```ts
type: 'project' | 'study'
```

React+TypeScript는 계획서에 명시돼 있다. 라우터 라이브러리는 확정되지 않았으며 이전 답변은 React Router를 기준으로 설명한 예시다.

### 13.3 남은 라우팅 결정

- `/`에서 로그인 여부에 따라 어디로 이동하는가.
- `/workspace/:workspaceId`를 팀 캘린더로 바로 연결하거나 리다이렉트할 것인가. 기본 화면이 팀 캘린더라는 제품 요구는 확정됐지만 구현 방식은 미정이다.
- 예약을 페이지 경로로 다룰지, 기존 화면 위 모달로 다룰지.
- 예약 모달에 직접 진입한 뒤 닫을 때 어디로 돌아갈지.
- 채팅방 목록만 선택한 상태를 별도 URL로 표현할지.
- 권한 없는 Workspace/채팅방/문서 경로와 존재하지 않는 경로의 처리.
- AI 진단·추천 화면의 상세 설계를 `/ai`에 어떻게 배치할지.

예약의 `/reservation` 경로 예시와 `ReservationModal` 제안은 동시에 등장했다. 이를 서로 다른 예약 기능 두 개로 확정하지 않고, 페이지와 모달의 관계를 후속 설계 대상으로 남긴다.

## 14. 공통 레이아웃과 컴포넌트 방향

### 14.1 제안된 3단 구성

```text
AppLayout
├─ GlobalSidebar
│  ├─ 접기/펼치기
│  ├─ 홈
│  ├─ Workspace 목록
│  ├─ 생성
│  └─ 설정
│
├─ WorkspaceSidebar: Workspace 선택 시 표시하는 채팅 탐색기
│  ├─ 프로젝트 이름
│  ├─ 채팅방 검색
│  ├─ Tag Group
│  └─ 채팅방 목록
│
└─ MainContent
   ├─ CalendarPage
   ├─ ChatPage
   ├─ MarkdownPage
   └─ ReservationPage 또는 예약 모달 연결
```

`AppLayout` 등의 이름은 이전 답변에서 제안한 컴포넌트 명칭이다. 실제 코드가 있거나 이미 구현됐다는 뜻은 아니다.

### 14.2 화면별 영역 표시 제안

| 화면 | 전체 탐색 1열 | 채팅 탐색 2열 | 메인 영역 |
|---|---|---|---|
| 전역 Dashboard | 표시 | 기본적으로 없음 | 개인 홈 |
| 전역 Calendar | 표시 | 기본적으로 없음 | 개인 통합 달력 |
| 전역 Reservation | 표시 | 기본적으로 없음 | 예약 페이지 또는 호출한 화면 위 모달 |
| Workspace Calendar | 표시 | 유지하는 방향 | 팀 캘린더 |
| Workspace Chat | 표시 | 유지 | 선택한 방의 대화 |
| Workspace Markdown | 표시 | 유지하는 방향 | 연결 문서 편집/조회 |
| Workspace Reservation | 표시 | 유지 여부 세부 미정 | 현재 공간이 지정된 공통 예약 기능 |

전역 화면에서 WorkspaceSidebar를 숨기는 것은 `Workspace 선택 시 표시`라는 후속 제안에 따른 기본안이다. 실제 표시 조건과 전역 이동 시 마지막 프로젝트 선택 상태의 보존 여부는 아직 정하지 않았다.

### 14.3 공통화의 범위

- 프로젝트·스터디 레이아웃 공통화.
- 전역/Workspace 예약의 공통 UI·기능 사용.
- 채팅 탐색 영역을 유지하면서 메인 콘텐츠 교체.
- 채팅방과 연결 문서 사이의 이동 관계 표현.

동일한 컴포넌트를 쓰더라도 캘린더의 데이터 범위와 일정 공개 규칙은 진입 위치에 따라 달라진다.

## 15. URL 상태와 일시적 UI 상태

### 15.1 URL이 관리하는 상태 제안

현재 프로젝트, 채팅방, 문서처럼 새로고침하거나 주소를 다시 열어도 같은 대상을 가리켜야 하는 정보는 URL에 둔다는 방향이다.

```ts
workspaceId
chatRoomId
documentId
```

### 15.2 화면 내부 상태 제안

사이드바가 접혔는지, 예약 창이 열렸는지, 태그 메뉴가 열렸는지 같은 일시적인 상태는 화면 내부 상태로 관리한다는 방향이다.

```ts
sidebarCollapsed
reservationModalOpen
selectedTagGroup
calendarFilter
```

이전 답변은 이를 React state라고 표현했고 계획서에도 React가 명시돼 있다. 다만 개별 상태의 저장 위치까지 확정한 것은 아니다. 필터나 사이드바 상태를 영구히 저장하면 안 된다는 규칙도 아니다. 새로고침·주소 공유·사용자별 설정 보존 요구를 정하면 일부 상태의 위치가 달라질 수 있다.

### 15.3 화면 상태 목록

이전 답변에서 직접 언급된 상태는 다음과 같다.

- 프로젝트 선택 안 됨 / 선택됨.
- 캘린더 화면 / Markdown 화면 / 예약 화면.
- 채팅방 선택 안 됨 / 선택됨.
- 좌측 1열 접힘 / 펼침.
- 예약 모달 닫힘 / 열림.
- 태그 드롭다운 닫힘 / 열림.
- 태그 그룹 선택 및 캘린더 필터.

**추가 검토 제안:** 빈 목록, 검색 결과 없음, 접근 불가, 저장 중, 예약 중복 등 예외 상태를 같은 와이어프레임에서 정의한다. 이는 구현 검토를 위한 보완이며 대화에서 이미 확정한 기능으로 취급하지 않는다.

## 16. 와이어프레임과 구현으로 내려가는 순서

### 16.1 이전 대화의 접근 순서

사용자가 “어케하는거임..?”이라고 물은 뒤 답변은 다음 순서를 제안했다.

```text
화면을 먼저 나눈다
→ URL을 정한다
→ 공통 레이아웃을 만든다
→ 각 화면을 컴포넌트로 나눈다
```

대화 후반의 초점은 기능을 계속 추가하는 것보다 현재 요구사항을 화면·상태·라우팅 구조로 구체화하는 데 있다. 다만 일부 권한과 AI 진단·결과의 상세 정책은 여전히 미정이다.

### 16.2 우선 그릴 여섯 화면

1. Dashboard.
2. 전역 Calendar.
3. 전역 Reservation.
4. Workspace 기본 Calendar.
5. Workspace Chat.
6. Workspace Markdown.

각 화면에서 `GlobalSidebar / WorkspaceSidebar / MainContent` 중 무엇이 보이는지 확인하자는 제안이었다.

AI와 설정이 이 여섯 화면에서 빠졌다고 해서 전체 기획에서 삭제된 것은 아니다. 이 목록은 먼저 구체화할 화면 묶음이며 전체 화면 수를 여섯 개로 제한하는 정책이 아니다.

### 16.3 설계를 구체화할 산출물 제안

| 산출물 | 정리할 내용 |
|---|---|
| 화면 목록 | 전역과 Workspace의 기능·진입점 |
| 와이어프레임 | 1열·2열·메인·상단바 배치 |
| 이동 관계 | 홈, 공간, 채팅, 문서, 예약 사이의 이동 |
| 권한 표 | 생성·열람·수정·삭제·초대·운영 관리 |
| 상태 표 | 선택됨/안 됨, 모달, 접힘, 빈 목록, 오류 |
| 컴포넌트 구조 | 공통 레이아웃과 화면별 콘텐츠 |
| 자료 대조표 | 계획서·스케치의 항목과 최종 설계의 대응 |

## 17. 개념 관계와 데이터 모델의 미정 범위

이 절은 확정된 관계를 보존하기 위한 개념 정리다. 실제 데이터베이스 테이블이나 API 명세를 확정하지 않는다.

```text
사용자
└─ 여러 프로젝트/스터디에 참여 가능

프로젝트/스터디
├─ 여러 채팅방
│  ├─ 방별 참여자
│  ├─ 채팅방에 붙는 태그
│  └─ 연결된 Markdown 회의록
├─ 프로젝트별 태그 그룹
│  └─ 순서를 가진 태그 목록
├─ 담당자·담당업무가 있는 일정
└─ 프로젝트 맥락에서 신청하는 동아리방 예약

개인 전역 캘린더
└─ 여러 활동에 걸친 개인 일정 확인
```

| 개념 | 확인된 관계 | 실제 구현에서 남은 내용 |
|---|---|---|
| Workspace | 프로젝트와 스터디의 공통 UI | 공통 엔티티 채택 여부 |
| Membership | 한 사람이 여러 활동에 참여 | 가입·탈퇴·역할 변경 정책 |
| ChatRoom | 한 활동에 여러 방 | 공개 범위, 방 삭제, 초대 정책 |
| TagGroup/Tag | 활동별 정의, 태그 순서로 방 정렬 | 개수·권한·정렬 예외 |
| MarkdownDocument | 채팅방에 연결된 회의록 | 연결 개수, 생성 시점, 저장·이력 |
| CalendarEvent | 담당자·업무·공개 범위를 다루는 일정 | 정확한 필드와 공개 모델 |
| Reservation | 프로젝트와 시간대를 고르는 공통 예약 | 상태 모델, 자원 수, 수정·취소 |

### 18.1 원본 WBS와 구현 여건

초기 답변에는 “WBS상으로는 현재 프로젝트당 1개 채팅방이 제일 안전함”이라는 판단이 있다. 원본 확보 후 확인한 WBS 8.1에는 실제로 `FastAPI WebSocket · 방 1개 고정`이라는 비고가 있다. 계획서 위험 대응에도 일정에 따라 활동별 한 방으로 제한한다고 적혀 있고 회의 캡처에는 구현 난도와 발표에 필요한 범위를 고려한 축소 논의가 있다.

**단일 채팅방이라는 초기 구현 범위**와 **다중 채팅방이라는 사용자의 원래 기획**을 모두 보존한다. 여러 방을 만들 수 있도록 설계를 구체화한 것만으로 기존 WBS와 팀 합의까지 자동 변경된 것은 아니다.

### 18.2 초기 답변의 화면 표현 해석

S2 답변에는 프로젝트 홈이나 일정으로 들어가면 “가운데 영역 자체가 달라지는 방식”이라는 표현이 있다. 이후 S4 답변은 2열을 채팅 탐색기로 두고 `MainContent`를 전환하는 구조를 더 명확히 제안했다. 사용자의 “좌측 2열은 어지간하면 채팅 고정”을 우선해서, 이 문서는 **채팅 탐색을 유지하고 메인 콘텐츠를 교체하는 방향**으로 정리한다. 초기 답변의 모호한 표현을 별도 확정사항으로 추가하지 않는다.

### 21.2 현재 운영 방식과 문제

계획서는 교내 정보보안동아리 CERT-IS가 매년 프로젝트·스터디 활동을 진행하며 공지는 카카오톡으로, 프로젝트·스터디 관리는 Notion으로 나눠 처리한다고 설명한다. 공통 목표 부분에는 카카오톡·Discord로 회의를 진행한 후 Notion에 진행 내용을 정리하는 흐름도 등장한다.

원본에 적힌 불편은 다음 여섯 가지다.

1. 프로젝트 현황을 Notion 페이지를 통해서만 관리한다.
2. 진행에 필요한 동아리방 예약을 구두 또는 카카오톡으로 협의한다.
3. Notion 공유 페이지 오류로 불편이 발생한다. 예시는 블록 삭제 불가다.
4. 캘린더가 없어 일정을 확인하려면 공지를 일일이 확인해야 한다.
5. 카카오톡에서 결정한 사안을 Notion에 추가로 정리해야 한다.
6. 신입부원이 자신에게 맞는 보안 분야를 파악하기 어려워 프로젝트·스터디 참여 결정이 늦어진다.

따라서 동아리 운영에 필요한 기능을 하나의 시스템으로 통합하고, 회의와 기록을 시스템 안에서 바로 처리하려는 것이 기획 배경이다. 채팅 기록을 원본으로 유지하고 Markdown으로 정리하려는 후속 설명은 특히 5번 문제와 연결된다.

```text
└─ 팀 B 구성원 → 팀 A 채팅방 접근 불가

추가 질문
└─ 독립 생성 팀 X → 임원이 열람할 수 있는가?
```

이 계층은 회의에서 나온 안이다. 시스템에 관리자와 임원진이 별개 역할인지, 팀이 반드시 동아리에 속해야 하는지, 관리자가 모든 방을 볼 수 있는지, 방 참여자 제한보다 관리자 권한이 우선하는지는 확정되지 않았다. 후속 대화의 방별 참여자 구성과 함께 재검토해야 한다.

### 24.4 채팅 범위의 세 단계

| 단계 | 내용 | 근거 |
|---|---|---|
| 원래 기획 | 여러 방, 태그 검색, 이후 태그 그룹·정렬로 구체화 | 회의 태그 발언, S2~S3 |
| 초기 구현·계획서 범위 | 프로젝트·스터디별 한 방, 날짜 구분선 대안 | 회의 3:14~3:16, 계획서 리스크, WBS 8.1 |
| 추가 상세 설계 | 방별 참여자, 같은 인원의 여러 방, 연결 회의록 | S2~S3 |

세 단계는 서로 다른 맥락의 기록이다. “방 하나로 먼저 구현”을 원래 기획의 삭제로 쓰거나 “다중 방이 원래 기획”을 이미 구현 완료한 것으로 쓰지 않는다.

### 24.5 회의록 논의의 현재 해석

회의에서 회의록을 나중에 추가하자는 의견이 있었지만, 바로 뒤에 최소 생성 기능과 임원진의 필요성이 논의됐다. 계획서에는 Markdown 작성·등록·조회가 계속 포함되어 있다. 후속 사용자 설명에서는 **채팅이 메인이고 방에 연계된 Markdown 회의록을 편집·조회한다**고 정리됐다.

따라서 현재 상세 설계는 연결 회의록을 유지하며, 실제 이번 학기 구현에서 어느 수준까지 할지는 작업 범위로 정한다. 회의록 작성 강제 여부, 관리자 열람으로 대체할지 여부, 자동 요약 도입은 확정하지 않는다.

### 24.6 제품 참고 방향

Slack·Notion·Discord라는 이름은 기능과 UI를 생각할 때의 참고다. Slack은 채팅방·태그 탐색의 인상을, Notion은 일정·기록 관리의 인상을 설명하는 대화 맥락으로 사용됐다. 이 제품들의 모든 기능을 복제하거나 외부 서비스 연동을 구현하자는 요구가 아니다. 특히 외부 Notion 캘린더 연동은 계획서에서 제외했다.

## 25. UI 스케치 판독과 레이아웃 연결

### 25.1 직접 확인되는 도형

스케치 원본은 1200×713 픽셀이다. 검은 배경에 밝은 선으로 그린 앱 틀과 다음 요소가 보인다.

- 화면 전체를 둘러싼 큰 사각 틀.
- 가로로 긴 상단 띠.
- 상단 우측의 최소화·최대화·닫기처럼 보이는 초록색 표식 세 개.
- 왼쪽 끝의 매우 좁은 세로 영역에 네모/원/더하기 같은 표식과 하단의 원형 표식.
- 그 오른쪽 왼편 영역 상단의 큰 타원형 표식.
- 왼편 영역 안쪽의 추가 세로 구분선.
- 세로로 배치한 여러 원형 표식, 두 묶음처럼 나뉘는 가로 경계와 손글씨.
- 원형 표식 오른쪽의 짧은 물결 모양 선들.
- 왼편 묶음을 구분하는 더 큰 세로선과, 오른쪽의 넓은 작업 공간.
- 작업 공간 중앙 부근의 세 타원형 표시 및 작은 선.

도형 중앙의 타원들은 구체 기능 이름이 적힌 버튼으로 판독되지 않는다. 세부 버튼 수, 카드 종류, 로딩 표시 같은 의미를 임의 부여하지 않는다.

### 25.2 후속 대화와 함께 해석할 수 있는 부분

| 스케치 요소 | 대화와 결합한 해석 | 확실성 |
|---|---|---|
| 왼쪽 끝의 좁은 세로 영역 | 전체 탐색 1열 | 사용자 설명과 일치하는 방향 |
| 더하기 표식 | 생성 진입의 후보 위치 | 모양은 확인, 구체 기능은 대화로 해석 |
| 하단 표식 | 설정 등의 하단 기능 후보 | 사용자 설명과 연결 가능, 아이콘 의미 자체는 미확정 |
| 왼편의 묶인 목록·짧은 선 | 활동 목록 및 채팅 탐색 영역의 후보 | 어느 열이 활동/채팅인지 완전 고정하지 않음 |
| 두 묶음과 손글씨 | 프로젝트·스터디 같은 목록 그룹일 수 있음 | 정확한 글자는 불명확, 추정으로 기록 |
| 오른쪽 넓은 공간 | 캘린더·채팅·Markdown 등 메인 작업 화면 | 후속 설명과 일치 |
| 상단 띠 | 상단바 또는 창 프레임 | 구체 소속·내용 미정 |

우측 상단 창 제어처럼 보이는 표식만으로 데스크톱 앱을 구현한다는 결정을 내리지 않는다. 계획서는 반응형 웹을 명시한다.

### 25.3 스케치와 3단 레이아웃의 관계

```text
상단바/창 틀: 실제 앱 상단바 내용은 미정

전체 탐색 | Workspace 내부 탐색 묶음 | 넓은 메인 작업 영역
          | ├─ 활동/그룹 목록 후보   | ├─ 기본 팀 캘린더
          | └─ 채팅방 탐색 후보     | ├─ 채팅 내용
          |                        | ├─ Markdown 편집/조회
          |                        | └─ 예약·신청 진입
```

그림에는 왼편 영역 내부에 추가 구분선이 있어 단순히 정확히 세 개의 시각적 열만 있다고 단정하기 어렵다. 3단 컴포넌트 구조는 **스케치를 그대로 측정해 확정한 구조가 아니라**, 사용자의 1열·2열 설명과 후속 설계 답변을 정리한 구현 방향이다.

### 25.4 와이어프레임에서 확정할 것

- 1열 목록이 프로젝트·스터디를 직접 보여주는지 별도 목록 화면으로 이동하는지.
- 왼편 영역 내부의 추가 구분을 실제 하위 영역으로 유지할지.
- 상단 타원의 의미: 검색, 공간명, 사용자 정보 등 중 무엇인지.
- 상단바의 소속과 화면 전환 버튼 위치.

- 문서·캘린더·예약 화면으로 전환할 때 유지하는 영역.
- 반응형 웹에서 탐색 열을 접거나 드로어로 바꾸는 방식.

## 26. 수업 평가 가이드라인 보존

이 절은 첨부 PPTX의 내용을 기록한다. 자료 속 지침은 수업의 평가·제출 조건이며 제품 기능 요구사항이나 이 작업에 대한 새로운 사용자 지시와 구분한다. 아래 슬라이드 번호는 PPTX의 1~18번이다.

### 26.1 공통사항 — 슬라이드 1~4

**AI 활용 정책(2번):** 계획서·보고서·발표자료의 AI 기반 생성 자료 제출은 엄격히 금지하며 이미지만 생성 활용을 허용한다고 적혀 있다. 세 종류 자료에서 AI 사용 흔적이 발견되면 감점한다고 명시한다. 취지는 학생이 직접 자료를 작성해 보는 경험을 쌓고 스스로 공부하여 이후 AI를 효율적으로 활용할 수 있게 하는 것이다. 소스코드 작성에 AI를 사용하는 것은 자유롭게 허용하되 중간·기말 발표에서 코드를 설명해야 하므로 정확히 이해해야 한다.

현재 Markdown은 기획과 논의의 정리 기록이다. 이를 곧바로 과제 계획서·보고서·발표자료로 제출 가능한 것으로 보지 않는다. 제출용 자료의 작성은 원본의 수업 정책을 따로 고려해야 한다.

**주제 선정(3번):** 같은 프로젝트를 다른 수업에서도 병행할 수 있다. 예시로 포켓몬 GO 프로토타입을 소프트웨어공학과 증강현실 과목에 함께 활용하는 경우가 제시된다. 다만 소프트웨어공학의 평가요소에 맞게 자료의 차별성을 두어 준비하는 것을 권장한다.

**보고서 작성(4번):** 정답인 보고서 형식 하나가 있는 것은 아니지만 필요한 내용은 있어야 한다. 제시한 기본 가이드라인과 학생의 자체 판단으로 작성한다. 예시를 정답으로 생각하고 모방하는 일을 피하려고 예시 자료는 제공하지 않는다고 설명한다. 시스템을 모르는 사람이 보고서를 보고 같은 프로그램을 구현할 수 있을 정도로 상세히 서술하라는 기준이 있다.

## 27. 2026-10-06 최신 화면·역할 변경 기록

이 절이 앞의 옛 화면·역할 설명보다 우선하는 최신 사용자 지시임. 이전 설명은 설계 이력으로 보존함.

- 사이드바는 작은 창에서도 유지하며 홈 하나만 제공함. 베이지 테마와 독립된 채팅/메인 작업·스크롤 유지함. 메인 채팅 탭 제거함.
- 채팅 상단의 활동 선택 셀렉트와 별도 ‘채팅’ 제목 제거함. 방 이름과 활동 이름, 검색·태그·설정·문서 아이콘만 표시함.
- 검색·태그·방 목록은 상단 아래로 메시지를 덮는 방식으로 확장함. 다른 영역을 밀지 않으며 메시지 입력창은 고정 확보함. 방 설정·태그 관리는 메인 공간의 창으로 처리함.
- 팀장은 활동 생성자가 최초 팀장이 되는 구조임. 다른 구성원에게 위임 가능함. 한 명이 여러 프로젝트/스터디의 팀장이 될 수 있음. 동아리 임원 여부와 활동별 팀장 관계는 독립적임.
- 임원진은 참여하지 않은 프로젝트/스터디도 조회 가능함. 개인 캘린더 기본 범위와 전체 활동 운영 조회를 분리함. 조회 권한을 비참여 대화 전송·문서 수정으로 확대하지 않음.
- 활동·구성원·위임·일정 CRUD·예약 변경/취소·방/태그 관리·문서 초안 복원/버전 충돌을 로컬 시제품에서 구현했음. 실제 API·인증·DB·WebSocket·Gemini는 미연결 상태임.

위 확정 지시 이외의 방/문서 1:1, 태그 복수 선택·관리 범위, 보관 상태, 예약 운영 권한·시간·기간 등은 구현 검토용 기본값임. 상세값은 `cert-is-wireframe/README.md`에 구분했음. 초안의 로컬 보관은 서버 자동 저장과 다르며 사용자가 문서 저장 버튼을 눌러야 저장본이 변경됨.

2026-10-06 전체 검토 84개 항목과 이번 반영 범위는 `CERT-IS_프로젝트_관리_개선_검토.md` 16절, 실제 FE 연결 계약 및 협업 순서는 `cert-is-wireframe/FE_API_연결_계약.md`, 검증 근거는 `cert-is-wireframe/검증_기록.md`로 분리했음. 원본 WBS의 담당자·일정·완료 상태는 임의로 변경하지 않았음.
